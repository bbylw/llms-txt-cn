`llms.txt` 的设计初衷是与现有 Web 标准和平共存、各司其职，而不是推翻既有基础设施。

## 标准职责全景对比

| 标准协议 | 核心受众 | 主要用途 | 部署位置 | 典型触发时机 |
| --- | --- | --- | --- | --- |
| **`/llms.txt`** | AI 智能体与大语言模型 | 提供精选目录、上下文摘要与 `.md` 链接 | 站点根目录或任意子路径 | 智能体辅助用户时**按需推理检索** |
| **`/robots.txt`** | 网络爬虫与索引器 | 声明抓取允许或禁止的访问边界 | 仅站点根目录 | 爬虫抓取或模型训练前校验权限 |
| **`/sitemap.xml`** | 搜索引擎爬虫 | 穷举站点全部可索引的 HTML 页面 URL | 站点根目录或声明路径 | 搜索引擎定期全站收录与更新 |
| **`/.well-known/`** | 协议客户端与安全校验器 | 遵循 RFC 8615 存放域名级元数据 | 仅源站根目录 | 发现域级配置或验证所有权 |

## 与 `robots.txt` 的互补关系

正如 `/robots.txt` 和 `/sitemap.xml` 在网站根目录采用约定俗成的固定文件名，且正如 `index.html` 为任意目录路径提供了人类可读的默认入口一样，`llms.txt` 为任意路径提供了大语言模型可读的默认概览入口。

`robots.txt` 与 `llms.txt` 服务于截然不同的目标：

- **`robots.txt`** 告知自动化工具哪些抓取访问被站点视为可接受的（例如用于搜索引擎索引爬虫）。
- **`llms.txt`** 则是按需使用的信息指南，服务于智能体在协助用户解决问题、需要了解某个主题时实时读取的上下文。

提案最初即预期 `llms.txt` 主要服务于**推理阶段（Inference）**而非**模型训练阶段（Training）**，过去两年的行业实践也印证了这一点，尽管训练数据管线同样可以利用其中的高质量信息。此外，`llms.txt` 还可以引用站点上使用的结构化数据标记，帮助大语言模型在具体语境中准确解读相关信息。

## 为何不采用 `/.well-known/`（RFC 8615）

有人曾探讨过利用保留前缀 `/.well-known/`（RFC 8615）来存放元数据文件。然而，Well Known URI 只能存在于**源站（Origin）根目录**之下。

在现实 Web 发布生态中，大量作者仅对共享主机上的某一个子路径拥有发布权限：例如 GitHub Pages 项目站（`username.github.io/project/`）可以在自己的项目目录内自由发布静态文件，但永远无法向主域名的 `/.well-known/` 写入文件。

正如 `index.html` 可以放在任意路径下一样，`/docs/llms.txt` 能够精准描述它所处的子路径范围，这是单一根目录位置无法表达的语义。只要你有权在某个路径下发布内容，就可以为该路径提供专属的 `llms.txt`。

## 为何 `sitemap.xml` 无法替代 `llms.txt`

`sitemap.xml` 列出的是站点上所有可供搜索引擎索引的人类可读网页清单，它无法替代 `llms.txt`，原因主要有三点：

1. **缺乏 LLM 友好版本**：`sitemap.xml` 通常不会列出专门为大语言模型准备的干净 Markdown 版本链接。
2. **无法包含外部关键参考**：它只能列出站内 URL，无法引入外部依赖库文档或相关站点链接，即便这些外部资源对理解当前项目至关重要。
3. **全量体积远超上下文限制**：站点地图覆盖全站全部页面，汇总起来往往远远超出大语言模型上下文窗口容量，并且包含大量对理解网站核心用法并不必要的冗余页面。
