初版 `llms.txt` 提案发布于 2024 年 9 月，彼时「语言模型会像人类一样常态化地浏览并读取网站内容」还属于前瞻性设想。此后的两年间，社区对这一提案的接纳速度远超预期：数千家网站发布了 `llms.txt` 文件，文档平台开始默认自动生成它们，各类编程智能体也已将其作为可靠入口日常使用。

**2026 年 8 月发布的 v2 修订版**，正是为了总结并规范这波真实落地浪潮中沉淀出的共识与需求。

## 1. 新增标准 Link 自动发现机制

大规模采纳带来了最迫切的共性需求——**可发现性（Discoverability）**。当智能体已经处于某个具体网页 URL 上时，如何无需靠猜就能找到该页面的 Markdown 版本，或找到涵盖该页面的那一份 `llms.txt`？

v2 给出了基于 Web 标准的明确答案：

- 使用 `rel="alternate" type="text/markdown"` 指向当前页面的干净 Markdown 版本。
- 使用 `rel="describedby"` 指向覆盖当前页面的 `llms.txt` 索引文件。

这两种关系既可以通过 HTML 页面中的 `<link>` 标签声明，也可以通过 HTTP `Link:` 响应头下发（响应头方式尤为适合 CDN 统一配置以及非 HTML 资源）。

## 2. 同时允许 `page.html.md` 与 `page.md`

v1 最初仅规定了一种 Markdown 页面 URL 形式，即在完整页面 URL 后直接追加 `.md`（例如 `page.html.md`）。

在实际工具链生态中，许多静态发布系统采用了「替换原扩展名」的方式（例如将 `page.html` 映射为 `page.md`）。v2 正式承认并同时允许这两种命名约定，降低了工具与站点迁移的摩擦成本。

## 3. 明确定义子路径作用域与最具体优先

v1 曾允许将 `llms.txt` 放在子路径下，但并未界定多层级共存时的语义边界。

v2 对此作出清晰定义：

- 一份 `llms.txt` 文件覆盖其所在路径及以下的所有页面。
- 当同一个页面被多个不同层级的 `llms.txt` 覆盖时，智能体应当采用**路径最具体**的那一份。

这一条明确了诸如 GitHub Pages 项目子站等「仅拥有子路径控制权」的作者也能完整参与整个生态。

## 4. 明确按需消费方式，移除 `llms_txt2ctx` 与 `Optional` 机械语义

v1 曾附带介绍过 `llms_txt2ctx` 工具，用于将整个 `llms.txt` 链接树一口气展开拼装为单一的大段 LLM 上下文，但当时并未正面说明智能体应当如何自主消费索引。

在 v2 中，规范直接确立了预期使用方式：**智能体查看或检索 `llms.txt` 定位所需条目，然后仅按需追踪相关链接并读取对应 Markdown 内容**。

随之调整的是：

- 上下文批量展开工具 `llms_txt2ctx` 不再作为规范本身的组成部分。
- 与之绑定的 `## Optional` 分组也不再承担「供展开工具自动剔除」的机械语义。`Optional` 分组依然完全合法，并继续作为标记次要延伸资料的实用惯例保留。
- 全文的背景说明与示例从「预测未来可能发生」改写为基于当前智能体真实工作方式的描述。
